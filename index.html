🤔 Think About It: Why can't a modern cloud server with 16 CPU cores just easily handle 10,000 login requests per second?

🚦 Rate Limiting 101: Metro Gates, HTTP 429 & Retry-After

75 XP · 🎟️ Gatekeeper Badge
"Kabhi Metro station ka automatic AFC gate dekha hai? Ek baar mein ek hi banda smart card tap karke nikal sakta hai. Agar 50 log ek sath gate todne ki koshish karenge toh 'BEEP BEEP' bajega aur gate lock! Yahi hai Rate Limiting."

Why can't our server just process every request as fast as possible?
Because servers have finite memory, database sockets, and third-party API quotas (like SMS gateways or bank payment switches).

A rate limiter sets a fair boundary: "You may send at most 10 requests every 60 seconds." If you exceed that limit, the server politely tells you to back off.

In simple words: HTTP 429 Too Many Requests means "Bhai slow down, you knocked too fast!", and the Retry-After header tells you "Wait 30 seconds before trying again."
🌍 Where You Encounter Rate Limits Every Day

🔐 Login Protection

Limit each IP to 5 failed attempts per 15 minutes. Stops brute-force password guessing dead in its tracks.

💸 UPI Payments API

Limit users to 3 OTP requests per minute. Prevents accidental double debits and saves hefty SMS vendor fees.

🐙 GitHub API

Gives developers 5,000 requests per hour with an authenticated token, or 60 per hour for anonymous users.

💳 Stripe Checkout

Default rate limit is about 100 operations/sec in live mode and about 25/sec in test mode per account, isolating buggy merchant loops.

📋 Common Rate Limiting HTTP Headers

When an API rejects or meters your request, response headers communicate status to client apps. (Note: Retry-After is a standardized HTTP header per RFC 7231 & RFC 6585, while X-RateLimit-* headers are a widely adopted convention rather than a formal standard): 

HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 30                      # "Wait 30 seconds before knocking again"
X-RateLimit-Limit: 100               # "Your max quota per window"
X-RateLimit-Remaining: 0             # "Zero tokens left right now"
X-RateLimit-Reset: 1700000030        # "Unix timestamp when your quota resets"

{
  "error": "Too Many Requests",
  "message": "ChaiPay rate limit exceeded. Please wait 30 seconds."
}
🤔 Think About It: Why is returning HTTP 429 with Retry-After so much better than just dropping the connection silently?
Predictable client behavior! When mobile apps or partner services see 429 with Retry-After: 30, their network libraries can automatically pause and retry after 30 seconds using exponential backoff. If you drop the connection silently, client apps think the network is dead and immediately hammer you with 10 aggressive retries, making server load 10x worse!
⚠️ Beginner Mistake: Returning 403 Forbidden instead of 429 Too Many Requests.
403 means "You are not allowed here at all (bad credentials or wrong role)." 429 means "You ARE allowed here, but you are knocking too fast right now! Try again shortly."
🏢 Why does this matter in real products? (Stripe & GitHub)
Stripe processes hundreds of billions of dollars annually. If a merchant's developer writes a runaway while(true) loop calling Stripe's payment endpoints, Stripe's rate limiters immediately return 429 to that merchant without affecting any other merchants in the world.
🎯 Mission 1 Key Takeaways
  • Rate limiting sets an allowed quota (e.g. 100 requests per minute) tracked per IP, user ID, or API key.
  • When clients exceed their quota, the server returns HTTP 429 Too Many Requests instead of crashing.
  • Response headers like Retry-After and X-RateLimit-Reset allow client apps to pause and retry gracefully.

🪣 The Token Bucket Algorithm: The Gold Standard

125 XP · 🪣 Token Master Badge
"College canteen ya mandir ka prasad counter yaad hai? Pehle counter se 5 token lo. Har plate samosa ke badle 1 token bouncer ko do. Jab token khatam, samosa band jab tak naya refill na mile!"
💡 Explanation Level

How Token Bucket Works: Imagine a bucket that holds a maximum capacity of capacity tokens. Tokens refill constantly at a fixed rate of refillRate tokens per second.

  • Every incoming request costs 1 token.
  • If tokens ≥ 1: Deduct 1 token, request is ALLOWED.
  • If tokens < 1: Request is REJECTED (429).
  • The bucket never overflows beyond its max capacity.

Imagine you have a small plastic cup that holds 5 shiny coins. Every second, an uncle drops 1 new coin into your cup. Every time you want to play an arcade game, you hand over 1 coin. If your cup is empty, you can't play until uncle drops another coin. If you don't play for a long time, the cup gets full and extra coins spill onto the floor (max 5 coins always)!

In simple words: Lazy Refill means: instead of running an expensive timer every second, we calculate tokens added only when a request actually arrives: tokens = min(capacity, current + elapsed * rate).

💻 Production JavaScript Implementation

Hover over or click each explanation step below to highlight the exact code line that executes it: 

class TokenBucket {
  constructor(capacity, refillRate, clock = Date.now) {
    this.capacity   = capacity;    // Max bucket size
    this.refillRate = refillRate;  // Tokens refilled per second
    this.clock      = clock;       // Injectable clock for deterministic tests
    this.tokens     = capacity;    // Bucket starts 100% full
    this.lastRefill = clock();     // Last refill timestamp (ms)
  }

  allowRequest(cost = 1) {
    const now     = this.clock();
    const elapsed = (now - this.lastRefill) / 1000; // Seconds since last request
    this.tokens   = Math.min(this.capacity, this.tokens + elapsed * this.refillRate);
    this.lastRefill = now;                          // Advance anchor timestamp

    if (this.tokens >= cost) {
      this.tokens -= cost;
      return true;  // 200 OK — Allowed
    }
    return false;   // 429 Too Many Requests — Throttled
  }
}
1
State Setup: Sets max burst capacity and steady refillRate. Bucket starts 100% full so new users don't encounter immediate cold-start 429 errors.
2
Injectable Clock: Takes an optional clock function (defaults to Date.now). This dependency injection allows test suites and simulators to freeze time without wall-clock sleeps.
3
Elapsed Calculation: Calculates exact seconds elapsed since the last request was checked: (now - lastRefill) / 1000.
4
Lazy Refill & Cap: Multiplies elapsed seconds by refill rate. Math.min(capacity, ...) strictly guarantees the bucket never exceeds its burst ceiling.
5
Anchor Timestamp Update: Updates this.lastRefill = now so subsequent requests only measure the next delta.
6
Quota Verification: Checks if remaining tokens are sufficient for this request's cost (default cost = 1).
7
Deduct & Decision: If allowed, deducts cost tokens and returns true. Otherwise returns false (HTTP 429).
🤔 Think About It: Why is lazy refill so much lighter on server memory than running a background setInterval() timer?
Imagine 500,000 active users logged into ChaiPay. If you used setInterval to add tokens every second, you would need 500,000 background timers running inside Node.js! That would melt the event loop. With lazy refill, you use ZERO timers. The math only runs when a user actually knocks on the API.
⚠️ Beginner Mistake: Forgetting Math.min(this.capacity, ...) in lazy refill.
With a refill rate of 2 tokens/sec, 24 hours idle (86,400 seconds) would give 172,800 tokens! Without Math.min, an idle user could bank all 172,800 tokens and fire a massive 172,800-request DDoS burst that completely overwhelms your server.
🏢 Why does this matter in real products? (AWS API Gateway)
Amazon Web Services (AWS) uses the Token Bucket algorithm for API Gateway throttling. They let you set both a steady-state rate (refill rate) and a burst capacity (bucket size), ensuring mobile apps can quickly load initial data on startup without getting throttled.
🎯 Mission 2 Key Takeaways
  • Token Bucket naturally handles bursts up to its capacity, providing a smooth user experience.
  • Lazy refill computes token growth on demand, requiring zero background timers or CPU overhead.
  • It uses constant O(1) memory per user — only two numbers (tokens and timestamp) need to be stored.

🪟 Fixed Window vs Sliding Window: The Boundary Burst Problem

150 XP · 🪟 Window Wizard Badge
"Fixed window mein ek fatal loop-hole hai! Agar limit 5 req/sec hai, aur koi 0.9 second pe 5 bhejta hai aur 1.1 second pe 5 aur, toh 0.2 second ke andar 10 requests server par ghus gayin! Isko bolte hain Boundary Burst!"
💡 Explanation Level

The Fixed Window Vulnerability: A Fixed Window resets its counter at rigid clock intervals (e.g., [10:00:00, 10:01:00)). If an attacker fires the full limit right before the window closes, and immediately fires another full limit right after the new window opens, 2x the traffic penetrates in a tiny fraction of a second.

Mom says: "You can have at most 2 chocolates between 1:00 PM and 2:00 PM, and 2 chocolates between 2:00 PM and 3:00 PM." A clever kid eats 2 chocolates at 1:59 PM and 2 chocolates at 2:01 PM! The kid ate 4 chocolates in just 2 minutes, but technically followed the rule! Sliding window fixes this loophole.

In simple words: A Sliding Window slides smoothly across time like a moving 60-second camera lens, so it never has artificial clock boundary resets.

🧮 Worked Math Example: How Sliding Window Counter Estimates Traffic

Let's trace the exact math with real numbers so there is zero mystery:

Step 1: Setup the Scenario
Quota Limit = 10 requests per minute (window size = 60 seconds).
In the previous minute (10:00 to 10:01), the user sent 8 requests.
Right now it is 10:01:15 (15 seconds into the current minute). The user has sent 2 requests so far.
Step 2: Calculate Current Time Offset
Current minute elapsed: 15s / 60s = 0.25 (25%).
Remaining weight of previous minute: 1 - 0.25 = 0.75 (75%).
Step 3: Calculate Weighted Estimate
Estimate = (Previous Window Requests × Weight) + Current Window Requests
Estimate = (8 × 0.75) + 2 = 6.0 + 2 = 8.0 requests.
Step 4: Decision
Can request #3 pass? 8.0 + 1 = 9.0 ≤ 10. ALLOWED! ✅
If the estimate had reached 10.0, request would be REJECTED (429)! ❌

Why is this an approximation? It assumes requests in the previous minute were evenly spread out over the 60 seconds. In rare cases where requests clustered at the very end of the previous window, it might allow or drop slightly more requests than the exact limit (this is the approximation trade-off). In practice, Cloudflare's engineering blog reported that roughly 0.003% of requests were wrongly allowed or limited, while saving over 99% of memory!

💻 Pure JavaScript: Sliding Window Log & Counter

Implementation 1: Sliding Window Log (Exact, O(N) memory) 

class SlidingWindowLog {
  constructor(limit, windowMs, clock = Date.now) {
    this.limit    = limit;
    this.windowMs = windowMs;
    this.clock    = clock;
    this.logs     = []; // Array of timestamps
  }

  allowRequest() {
    const now    = this.clock();
    const cutoff = now - this.windowMs;

    // Drop timestamps that fell outside the sliding window
    while (this.logs.length > 0 && this.logs[0] <= cutoff) {
      this.logs.shift();
    }

    if (this.logs.length < this.limit) {
      this.logs.push(now);
      return true;  // Allowed
    }
    return false;   // 429 Too Many Requests
  }
}

Implementation 2: Sliding Window Counter (Approximation, O(1) memory) 

class SlidingWindowCounter {
  constructor(limit, windowMs, clock = Date.now) {
    this.limit         = limit;
    this.windowMs      = windowMs;
    this.clock         = clock;
    this.prevCount     = 0;
    this.currCount     = 0;
    this.currentWindow = Math.floor(clock() / windowMs);
  }

  allowRequest() {
    const now       = this.clock();
    const curWindow = Math.floor(now / this.windowMs);

    // Check if time moved into a new window
    if (curWindow > this.currentWindow) {
      this.prevCount     = (curWindow - this.currentWindow === 1) ? this.currCount : 0;
      this.currCount     = 0;
      this.currentWindow = curWindow;
    }

    // Calculate weight of previous window
    const timeInWindow = now % this.windowMs;
    const weight       = 1 - (timeInWindow / this.windowMs);
    const estimate     = this.prevCount * weight + this.currCount;

    if (estimate + 1 <= this.limit) {
      this.currCount++;
      return true;  // Allowed
    }
    return false;   // 429 Too Many Requests
  }
}
1
State Setup: Stores limit and windowMs. Tracks only two counters (prevCount and currCount), guaranteeing strictly O(1) constant memory.
2
Epoch Window Alignment: Computes current discrete window bucket ID Math.floor(now / windowMs).
3
Window Slide / Rollover: If the clock moved to the next window, the current count slides to become prevCount. If 2+ windows skipped, previous resets to 0.
4
Overlap Weight Calculation: Measures progress inside the current window (e.g. 15s in a 60s window = 25%). Previous window weight is 1 - 0.25 = 0.75.
5
Weighted Linear Estimation: Computes smooth rolling estimate: prevCount * weight + currCount.
6
Boundary Check: Tests whether adding this request fits within limit: estimate + 1 <= this.limit.
7
Update & Response: If permitted, increments this.currCount++ and returns true. Otherwise returns false (HTTP 429).
🤔 Think About It: If Sliding Window Log is 100% mathematically exact, why don't massive platforms with 500 million active users use it for all requests?
Memory disaster! If each user sends 100 requests per minute, storing 100 64-bit integer timestamps for 500 million users would require 400 Gigabytes of fast RAM in Redis just for rate limiting metadata! Sliding Window Counter achieves near-perfect accuracy using only two simple integers (prevCount and currCount), fitting in a tiny fraction of that memory.
⚠️ Beginner Mistake: Thinking Sliding Window Counter is broken because the estimate is a float with decimals (like 4.7).
Decimals are completely normal and expected! The weighted average interpolates between the previous and current window. Checking estimate + 1 <= limit handles decimal estimates perfectly.
🏢 Why does this matter in real products? (Cloudflare Edge)
Cloudflare handles over 55 million HTTP requests every single second across global edge servers. They use the Sliding Window Counter algorithm because it evaluates in microseconds with constant O(1) memory, stopping massive multi-gigabit DDoS attacks without memory spikes.
🎯 Mission 3 Key Takeaways
  • Fixed Window algorithms suffer from boundary bursts, allowing up to 2x the limit across window boundaries.
  • Sliding Window Log achieves 100% precision by storing timestamps, but consumes O(N) memory which explodes under scale.
  • Sliding Window Counter combines the O(1) low-memory footprint of Fixed Window with the smooth boundary protection of Sliding Window.

🌐 Production Rate Limiting: Express.js, Redis & Lua Scripts

100 XP · ⚡ Cloud Master Badge
"Jab ChaiPay ke 50 server pods chal rahe hote hain, toh in-memory JavaScript variables dher ho jaate hain! Ek request Pod 1 pe jayegi, doosri Pod 2 pe. Dono ko pata hi nahi ki user ne 10 baar try kar liya! Yahan entry hoti hai centralized Redis ki!"

The Multi-Server Trap: In your local Node.js app, const rateLimits = new Map() works fine. In production, a load balancer distributes traffic across 10 or 100 server instances.

In simple words: A Race Condition (TOCTOU: Time-of-Check to Time-of-Use) happens when two servers check the token count at the exact same millisecond: both see 1 token left, and both approve — double-spending the quota!
In simple words: An Atomic Operation is a command that executes completely from start to finish without any other server being able to interrupt in the middle.
🚀 Express.js Production Middleware (Token Bucket)

How you wire a Token Bucket rate limiter into an Express.js backend with standard 429 status and response headers (runnable version available in examples/server.js): 

const express = require('express');
const { TokenBucket } = require('./js/ratelimiter');

// Map storing an in-memory TokenBucket per client: Map<string, TokenBucket>
const clientBuckets = new Map();
const CAPACITY = 10;
const REFILL_RATE = 2; // 2 tokens per second

function rateLimiterMiddleware(req, res, next) {
  // Key choice: client IP, authenticated user ID, or API key
  const clientKey = req.headers['x-api-key'] || req.user?.id || req.ip;

  if (!clientBuckets.has(clientKey)) {
    clientBuckets.set(clientKey, new TokenBucket(CAPACITY, REFILL_RATE));
  }
  const bucket = clientBuckets.get(clientKey);

  // Common Rate Limiting HTTP Headers
  res.setHeader('X-RateLimit-Limit', CAPACITY);

  if (bucket.allowRequest(1)) {
    res.setHeader('X-RateLimit-Remaining', bucket.getRemaining());
    return next();
  }

  // Rate limit exceeded (HTTP 429)
  const retryAfter = bucket.secondsUntilAvailable(1);
  res.setHeader('X-RateLimit-Remaining', 0);
  res.setHeader('Retry-After', retryAfter); // Standard HTTP header (RFC 7231)

  return res.status(429).json({
    error: 'Too Many Requests',
    message: 'ChaiPay rate limit exceeded. Please slow down.',
    retryAfterSeconds: retryAfter
  });
}

🔑 Choosing Your Rate Limiter Key:

🌐 Per-IP (req.ip)

Pros: Works on unauthenticated endpoints (signup/login).
Cons: College hostels and corporate offices share one public IP (NAT), unfairly throttling all students together. Mobile networks also rotate IPs rapidly.

👤 Per-User ID (req.user.id)

Pros: Fair per customer across devices; attackers cannot bypass by switching IPs or using a VPN.
Cons: Only works for logged-in users; useless on public /login endpoints.

🏷️ Per-API-Key (x-api-key)

Pros: Industry gold standard for B2B developer platforms (Stripe, GitHub); permits tiered limits (Free vs Pro tiers).
Cons: Requires managing and securely issuing API keys.

⚠️ In simple words: Memory Leak Danger with In-Memory Maps!
If 1 million distinct IPs hit your server over a month, clientBuckets.set(ip, ...) retains 1 million objects forever in RAM. In Node.js, always implement a cleanup strategy: a periodic interval deleting idle buckets whose tokens have refilled back to full, an LRU cache with a maximum size ceiling, or offload state to Redis with automatic TTL expiration.
⚡ Distributed Redis: Fixed Window Counter (Lua Script)

Why Redis Lua scripts? Because Redis runs Lua scripts atomically on a single thread. No other server pod can read or write in the middle! 

-- KEYS[1]: User rate limit key (e.g. "rl:user:9876")
-- ARGV[1]: Window size in seconds (e.g. 60)
-- ARGV[2]: Max allowed requests (e.g. 10)

local current = redis.call('INCR', KEYS[1])

-- CRITICAL: Only set EXPIRE on the FIRST request of the window!
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end

if current > tonumber(ARGV[2]) then
  return 0  -- REJECT (HTTP 429)
else
  return 1  -- ALLOW (HTTP 200)
end
💡 Why only set EXPIRE when current == 1?
If you called EXPIRE on every request, an attacker sending 1 request every 10 seconds would constantly push the TTL timer forward back to 60s! The key would live in Redis forever, and the user's quota would never reset back to 0. By checking if current == 1, the timer starts only on the first request and counts down steadily to 0, guaranteeing an honest reset window.
⚠️ Architecture Alert: Fixed Window Boundary Weakness!
Notice this simple Redis script is a Fixed Window counter, meaning it still carries the boundary burst vulnerability from Mission 3 (an attacker can send 2x the limit across the window edge). To fix this in production Redis:
  • Option A (Exact): Use a Redis Sorted Set (ZSET) storing each timestamp as both score and member, pruning with ZREMRANGEBYSCORE.
  • Option B (O(1) Memory): Use the Sliding Window Counter weighted two-key approach (storing current_window and previous_window counters).
In simple words: Clock Skew means tiny millisecond differences between physical server clocks on AWS; this script is completely immune to physical server clock skew because Redis server TTL handles expiration internally on its own clock!
🤔 Think About It: What happens to Redis memory if you rate-limit by IP address without an EXPIRE TTL?
Memory leak catastrophe! Over weeks, millions of unique IP addresses from mobile cellular networks visit your site. If keys never expire, Redis will eventually fill all 16GB of RAM with stale IP addresses, run out of memory (OOM), and crash your entire production database.
⚠️ Beginner Mistake: Executing await redis.get() followed by await redis.set() in JavaScript.
Between your get and your set, fifty other server pods can execute! That is the textbook definition of a race condition. Always bundle multi-step operations into a single atomic Redis Lua script.
🏢 Why does this matter in real products? (Flash Sales & Payment Gateways)
During major e-commerce flash sales and festival ticket bookings, thousands of backend server pods concurrently process checkout and payment callbacks. Atomic Redis scripts guarantee accurate counters and idempotency, ensuring no user is double-charged even if their mobile app double-taps "Pay Now".
🎯 Mission 5 Key Takeaways
  • In-memory rate limiters fail across multiple server nodes; centralized storage like Redis is required.
  • Redis Lua scripts eliminate race conditions (TOCTOU) by executing read-and-update steps atomically.
  • Set TTL only on the first request (current == 1) so the countdown timer does not reset indefinitely.

allowRequest() {
  const now     = this.clock();
  const elapsed = (now - this.lastRefill) / 1000;
  this.tokens   = Math.min(this.capacity, this.tokens + elapsed * this.refillRate);
  this.lastRefill = now;

  if (this.tokens >= 1) {
    this.tokens -= 1;
    return true;
  }
  return false;
}
